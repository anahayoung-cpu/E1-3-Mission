# Mini NPU Simulator

## 1. 프로젝트 개요

이 프로젝트는 AI 연산의 기초인 MAC(Multiply-Accumulate, 곱셈-누산) 연산을 Python의 반복문으로 직접 구현한 콘솔 프로그램입니다. 입력 패턴과 두 필터를 같은 위치끼리 곱한 뒤 합산하고, 점수를 비교해 십자가(Cross) 또는 X 패턴을 판정합니다. NumPy와 같은 외부 라이브러리는 사용하지 않았습니다.

### 학습 목표

- 2차원 리스트를 사용하여 N×N 패턴·필터를 저장하고 검증하기
- MAC 연산과 필터 점수 비교 원리 이해하기
- JSON 키와 라벨을 정규화하여 일관되게 분석하기
- 부동소수점 오차를 고려해 epsilon 기반 동점 판정하기
- 반복 측정과 연산 횟수로 시간 복잡도 O(N²) 설명하기
- 데이터/스키마 오류와 판정 정책에 따른 FAIL을 구분하기

## 2. 개발 환경 및 파일 구성

## 4. 구현 내용

### 4.1 행렬 구조 및 검증

패턴과 필터는 숫자로 이루어진 2차원 리스트로 저장합니다. `is_square_matrix(matrix, n)`는 리스트 여부, 행 개수, 각 행의 열 개수, 각 원소의 숫자 자료형을 검사합니다. 사용자 입력 모드의 `input_matrix()`는 `input()`, `split()`, `float()`와 `try/except`를 이용해 한 행씩 검증하고 저장합니다.

### 4.2 MAC 연산

`mac(matrix_a, matrix_b)`는 두 배열의 크기·형식을 확인하고 다음처럼 이중 반복문으로 같은 위치의 값을 곱해 누적합니다.

```python
n = len(matrix_a)
total = 0
for i in range(n):
    for j in range(n):
        total += matrix_a[i][j] * matrix_b[i][j]
return total
```

수식으로는 다음과 같습니다.

**MAC 점수 = Σ(i=0…N−1) Σ(j=0…N−1) 입력[i][j] × 필터[i][j]**

3×3 십자가 패턴을 십자가 필터와 비교하면 5점, X 필터와 비교하면 1점이 나옵니다. 따라서 십자가 쪽 필터 점수가 높습니다. 이 점수는 위치별 곱의 합이며, 별도의 정규화된 거리 척도는 아닙니다. 예컨대 0/1 패턴과 0/1 필터의 MAC 점수는 0부터 필터 내 1의 개수까지 나올 수 있지만, 실수와 음수 입력까지 허용하는 현재 프로그램에서는 이 범위가 보장되지 않습니다. 서로 다른 크기의 점수를 직접 비교하려면 기준을 명확히 정한 정규화(예: 0/1 필터의 최대 점수로 나누기)가 추가로 필요할 수 있습니다.

### 4.3 JSON 라벨 정규화

`normalize_label(label)`은 앞뒤 공백을 제거하고 소문자로 바꾼 다음, 다음의 표준 라벨로 통일합니다.

| 원본 표기 | 내부 표준 라벨 |
|---|---|
| `+`, `cross`, `Cross`, `plus`, `PLUS`, `십자가` | `Cross` |
| `x`, `X` | `X` |

`expected` 값과 필터 키에 동일한 정규화 규칙을 적용해 표기 방식 때문에 판정 비교가 틀리지 않도록 했습니다. 알 수 없는 값은 `None`으로 처리하여 해당 케이스를 FAIL로 기록합니다.

### 4.4 라벨 확장 절차

**확인된 구현 범위:** 최종 분류는 `Cross`와 `X` 두 가지입니다. 신규 라벨 `plus`와 `십자가`를 Cross의 **별칭**으로 추가하고, Python REPL에서 `normalize_label()`의 반환값을 직접 검증했습니다. 기존 라벨과 잘못된 입력에 대한 회귀 테스트도 통과했습니다. 별칭 추가는 분류 수를 늘리는 작업과 다릅니다.

#### A. 기존 라벨의 **새 별칭** 추가: 예를 들어 `plus` → `Cross`

1. **입력 규칙 결정:** 새 별칭 `plus`가 기존 Cross와 동일한 의미임을 정하고, 대소문자·공백 처리 규칙을 유지합니다.
2. **정규화 규칙 수정:** `LABEL_MAP` 딕셔너리에 입력 별칭과 표준 라벨의 대응 관계를 모읍니다.

   ```python
   # 테스트한 확장 규칙을 표현한 핵심 코드 예시
   LABEL_MAP = {
       "+": "Cross", "cross": "Cross", "plus": "Cross",
       "십자가": "Cross", "x": "X",
   }

   def normalize_label(label):
       if not isinstance(label, str):
           return None
       return LABEL_MAP.get(label.strip().lower())
   ```

3. **필터 키·정답 라벨에 함께 적용:** `expected`와 `filters[size_N]`의 키 모두 같은 `normalize_label()`을 거쳐 `Cross`/`X`로 변환되게 합니다. 단, `cross`와 `plus` 키가 **동시에** 존재하는 경우 동일한 표준 라벨로 충돌할 수 있으므로 중복 키를 감지해 FAIL 처리하거나 데이터 작성 규칙에서 하나만 허용하도록 정합니다.
4. **판정·출력 일관성 확인:** `predict_label()`의 두 점수 계산, `decide_label()`의 `Cross`/`X`/`UNDECIDED` 반환과 PASS/FAIL 비교는 그대로 유지합니다. 화면에는 별칭 `plus`가 아니라 표준 라벨 `Cross`로 표시되어야 합니다.
5. **테스트 케이스 추가:** 실제 REPL에서 신규 `plus`·`십자가`, 기존 `+`·`cross`·`x`·`X`, 공백·대소문자(`"  PLUS  "`), 미지원 `triangle`, 잘못된 자료형(정수·`None`)을 테스트했습니다. 기존 JSON 분석 6개 케이스의 판정 결과가 유지되는지도 확인했습니다. `expected` 및 필터 키를 별칭으로 바꿔 읽는 **JSON 통합 테스트는 정규화 이전 원본 값까지 로그로 남기면 더욱 명확하게 재현**할 수 있습니다.
6. **예상 결과 검증:** 정상 별칭은 `Cross`, 미지원/잘못된 자료형 입력은 `None`으로 처리됨을 `assert`로 확인했습니다. 프로그램 전체 실행에서는 `Cross`와 `X` 표준 라벨로 출력되는 기존 결과가 유지되었습니다.

| 확장 테스트(검증 기준) | 기대 정규화 결과 | 기대 동작 |
|---|---|---|
| `expected: "plus"` | `Cross` | Cross 예측 시 PASS |
| 필터 키 `"plus"` | `Cross` | Cross 필터로 읽음 |
| `" PLUS "` | `Cross` | 공백/대문자 무시 |
| `"+"`, `"cross"` | `Cross` | 기존 동작 유지 |
| `"triangle"` | `None` | 잘못된 라벨 FAIL |

#### B. **새로운 분류 클래스** 추가: 예를 들어 `Triangle`

이것은 별칭 추가와 다르게 **현재의 2개 필터 비교 구조 자체를 바꿔야** 합니다.

1. 표준 라벨 집합을 `Cross`, `X`, `Triangle`로 확장하고 `normalize_label()`에 `triangle` 등의 표기를 추가합니다.
2. JSON의 크기별 `filters`에 `triangle` 필터를 추가하고, 모든 필터와 입력 패턴의 N×N 형식을 검증합니다.
3. `predict_label()`을 고정된 두 필터 비교에서 **여러 필터의 점수를 반복 계산해 최고 점수를 선택하는 구조**로 변경합니다.
4. 최고 점수와 다음 점수의 차이가 epsilon보다 작으면 `UNDECIDED`로 판정하도록 다중 클래스 동점 정책을 정의합니다.
5. 출력 및 PASS/FAIL 비교가 새로운 표준 라벨 `Triangle`도 처리하도록 수정합니다.
6. Triangle 정답/오답/동점, 누락 필터, 기존 Cross/X 결과에 대한 테스트를 추가해 회귀 검증합니다.

#### C. 실제 수행한 신규 라벨·회귀 테스트 결과

Windows PowerShell에서 `python`을 실행한 뒤 `from main import normalize_label`로 함수를 가져와 아래 명령을 테스트했습니다. **`assert`가 실패했다면 `AssertionError`가 발생하지만, 실제로는 오류 없이 다음 명령으로 진행**했습니다.

```python
from main import normalize_label

# 새 별칭 — 실제 성공
assert normalize_label("plus") == "Cross"
assert normalize_label("십자가") == "Cross"

# 기존 별칭 회귀 검사 — 실제 성공
assert normalize_label("+") == "Cross"
assert normalize_label("cross") == "Cross"
assert normalize_label("x") == "X"
assert normalize_label("X") == "X"

# 공백·대소문자와 비정상 값 — 실제 성공
assert normalize_label("  PLUS  ") == "Cross"
assert normalize_label("triangle") is None
assert normalize_label(123) is None
assert normalize_label(None) is None

print("라벨 정규화 테스트 전체 PASS")
```

실제 콘솔에 `라벨 정규화 테스트 전체 PASS`가 출력되었습니다. 또한 이어 실행한 `python main.py`의 **원본 JSON 분석**에서 6건 중 PASS 3건, FAIL 3건으로 이전 결과와 동일해 기존 판정 로직이 유지되는 것을 확인했습니다.

> **검증 기록의 한계:** JSON 분석 콘솔에는 정규화된 `expected`만 출력하므로, 실행 로그만으로 JSON 파일에 `plus`·`십자가`를 넣어 실행한 시점과 원본 값을 직접 증명할 수는 없습니다. 신규 별칭의 **함수 단위 검증은 완료**했으며, JSON 입력 경로까지 입증하려면 테스트 당시의 `data.json` 변경 기록 또는 원본 라벨 출력 로그를 함께 보관해야 합니다. 별칭 추가는 현재의 `Cross`/`X` 두 분류를 유지하는 작업이며, `Triangle`과 같은 세 번째 분류를 만드는 작업은 위 B절의 별도 개발이 필요합니다.

### 4.5 epsilon 기반 동점 비교 #compare_scores

부동소수점 계산에서는 수학적으로 같은 값이어도 저장·계산 과정에서 매우 작은 차이가 나타날 수 있습니다. 이를 고려해 `EPSILON = 1e-9`로 설정했습니다. 이 값은 **이번 과제에서 제시한 권장 기준**을 그대로 채택한 것이며, 데이터의 점수 크기·측정 오차를 분석해 최적화한 값은 아닙니다. 큰 스케일이나 0에 매우 가까운 값을 함께 다룬다면 절대 허용오차와 상대 허용오차를 함께 검토해야 합니다.

```python
if abs(cross_score - x_score) < EPSILON:
    return 0   # 동점
```

- Cross 점수가 더 높으면 `Cross`(사용자 입력 모드에서는 A)
- X 점수가 더 높으면 `X`(사용자 입력 모드에서는 B)
- 점수 차이가 epsilon보다 작으면 `UNDECIDED`(사용자 입력 모드에서는 판정 불가)

JSON 모드에서 판정 결과와 `expected`의 표준 라벨이 일치할 때만 PASS로 처리합니다. `expected`가 Cross 또는 X인데 판정이 `UNDECIDED`이면 FAIL입니다.

### 4.6 성능 측정 #measure_mac_time

`measure_mac_time()`은 `time.perf_counter()`로 `mac()` 호출 직전과 직후의 시간을 측정합니다. 각 행렬 크기에서 10회 반복한 경과 시간의 평균을 구하고 `×1000`하여 밀리초(ms)로 표시합니다. 출력·입력·파일 읽기 시간은 측정 구간에 포함하지 않습니다. 현재 `mac()`이 자체적으로 행렬 형식을 검증하므로, 측정값에는 **입력 행렬 검증과 곱셈·누적 연산 시간**이 모두 포함됩니다.

성능 비교에는 `generate_matrix(n)`으로 만든 동일 크기의 **모든 원소가 1인 두 행렬**을 사용했습니다. 이 표는 JSON에 저장된 실제 패턴의 인식 성능이 아니라 행렬 크기에 따른 함수 실행 시간을 비교한 것입니다.

```text
size_N 필터 존재 확인 ── 누락 ────> FAIL 사유 기록 ──┤
        |                                         |
        v                                         |
라벨·행렬 크기·숫자 검사 ─ 오류 ──> FAIL 사유 기록 ──┤
        |                                         |
      정상                                        |
        v                                         |
MAC 계산 → epsilon 판정 → expected 비교 → PASS/FAIL ┤
                                                  |
                                                  v
                                          다음 패턴 계속 분석
```

각 패턴의 검증 실패는 해당 패턴을 FAIL로 집계하고 `continue`로 다음 패턴으로 넘어갑니다. 다만 **파일 자체가 없거나 JSON 문법이 깨진 경우**를 처리하는 예외 로직은 현재 별도로 구현하지 않았습니다.

### 4.8 CPU와 NPU의 처리 차이 및 병목 분석

> **이 프로젝트는 실제 NPU를 구동하지 않습니다.** Python의 CPU 실행으로 MAC의 *계산 원리*만 재현하므로 아래 비교는 하드웨어 일반 원리의 설명이며, 이 프로젝트의 CPU/NPU 실측 성능 비교 결과가 아닙니다.

| 비교 기준 | 일반적인 CPU | 일반적인 NPU(행렬 연산 가속기) |
|---|---|---|
| 주된 설계 목표 | 다양한 명령·분기·제어 흐름의 범용 처리 | 반복적 곱셈·누적 연산의 높은 처리량과 효율 |
| MAC 실행 방식 | 한 Python 반복문은 순차적으로 진행되지만 CPU 자체는 SIMD·다중 코어 병렬 처리 가능 | 다수의 연산 유닛·행렬 연산 구조로 MAC를 병렬 수행하도록 설계 |
| 잘 맞는 작업 | 적은 양의 계산, 복잡한 분기, 유연한 작업 처리 | 충분히 큰 행렬·텐서의 대량 반복 계산 |
| 흔한 병목 | Python 인터프리터 오버헤드, 메모리 접근, 캐시 미스, 메모리 대역폭 | 데이터 공급을 위한 메모리 대역폭, 온칩 메모리 용량, 데이터 이동·전송 비용, 연산 유닛 활용률 |

**예시: 25×25 MAC 한 번은 625개 위치의 곱셈·누적을 필요로 합니다.** 현재 `mac()`의 두 중첩 `for`는 각 위치를 Python에서 순서대로 처리합니다. 행렬이 커지면 연산 자체뿐 아니라 매 원소 접근 및 행렬 형식 검사에도 시간이 듭니다. 반면 NPU는 여러 MAC를 동시에 처리할 수 있도록 설계되지만, **필요한 데이터를 제때 공급하지 못하면** 연산 유닛이 대기하여 이론상 병렬 성능을 다 쓰지 못할 수 있습니다.

- **연산 병목(compute-bound):** 계산량이 많고 데이터 재사용이 충분하면 연산기의 곱셈·누적 처리량이 성능을 제한할 수 있습니다.
- **메모리 병목(memory-bound):** 데이터 재사용이 적거나 배열이 캐시/온칩 메모리에 잘 맞지 않으면 연산기보다 데이터를 불러오는 속도(대역폭·지연)가 성능을 제한할 수 있습니다.
- **전송·실행 준비 오버헤드:** 아주 작은 3×3처럼 작업량이 적을 때는 NPU로 데이터를 옮기고 실행을 준비하는 비용이 계산 이득보다 클 수도 있습니다. 따라서 **모든 작업에서 NPU가 CPU보다 빠른 것은 아닙니다**.

**개선 방향:** 반복되는 데이터 검증을 계산 구간 밖으로 이동하고, 블로킹/타일링으로 가까운 데이터 재사용을 높이며, 적절한 병렬화·배치 처리를 고려할 수 있습니다. 이번에는 별도 `cpu_test.py`에서 **2D/1D 접근을 직접 비교**했으며, 실제 NPU 연산이나 하드웨어 메모리 대역폭은 측정하지 않았습니다. 어떤 기법이 유리한지는 하드웨어·데이터 크기에 따라 달라집니다. 자세한 실측 결과는 §5.5를 참고합니다.

### 5.4 시간 복잡도 O(N²) 분석

1. N×N 행렬의 MAC 연산은 모든 행과 열 위치에 대해 곱셈과 누적 덧셈을 수행합니다.
2. `mac()`에는 `for i in range(n)`과 그 안의 `for j in range(n)`이 있습니다.
3. 바깥 반복문은 N번 실행되고, 안쪽 반복문도 각 바깥 반복마다 N번 실행됩니다.
4. 따라서 한 번의 MAC 계산에서 위치별 곱셈은 총 N×N = N²번 수행됩니다.
5. 3×3 행렬은 9번, 5×5 행렬은 25번의 곱셈이 필요합니다.
6. 13×13 행렬은 169번, 25×25 행렬은 625번의 곱셈이 필요합니다.
7. 행렬 한 변의 길이가 커질수록 처리해야 할 원소의 수가 제곱 비율로 늘어납니다.
8. 이번 실행에서 평균 측정 시간은 3×3의 `0.008400 ms`에서 25×25의 `0.148180 ms`로 증가했습니다.
9. 25×25의 연산 횟수는 3×3의 약 69.4배이고, 이번 측정 시간은 약 17.6배입니다.
10. 두 비율이 정확히 일치하지 않는 이유는 Python 함수 호출, 행렬 검증, 타이머 측정 오버헤드 및 운영체제 실행 환경 등이 영향을 주기 때문입니다.
11. 또한 각 크기당 10회만 측정했으므로 작은 행렬에서는 측정 변동성이 상대적으로 크게 나타날 수 있습니다.
12. 실제로 시간 복잡도 O(N²)의 직접적인 근거는 측정 시간의 비율이 아니라 **모든 N×N 위치를 방문하는 중첩 반복문 구조**입니다.
13. `mac()` 내부의 행렬 형식 검증 또한 N²개의 요소를 검사하므로, 검증을 포함한 현재 함수의 전체 시간 복잡도 역시 O(N²)입니다.
14. 따라서 본 시뮬레이터는 행렬 크기가 증가함에 따라 MAC 계산량과 처리 시간이 대체로 늘어나는 특성을 확인하는 데 의미가 있습니다.

*시간 복잡도:처리해야 할 데이터가 많아지면 컴퓨터가 해야 하는 일이 얼마나 늘어나는가?

시간 복잡도 O(N²) 설명

시간 복잡도는 데이터 크기가 커질 때 컴퓨터의 작업량이 얼마나 증가하는지 나타내는 개념.

MAC 연산에서는 이중 for문을 사용해 행과 열을 모두 계산하기 때문에 N × N번 연산.

예를 들어,
- 3×3 행렬 → 9번 연산
- 5×5 행렬 → 25번 연산
- 25×25 행렬 → 625번 연산
즉, 행렬 한 변의 크기가 2배 커지면 연산 횟수는 4배 증가.

이처럼 작업량이 N의 제곱에 비례해서 증가하는 것을 O(N²) 이라고 함.

단, 실제 실행 시간은 컴퓨터 환경 등에 따라 연산 횟수와 정확히 같은 비율로 증가하지 않을 수 있음.

예) mac() 함수의 작업
- 행렬이 리스트인지 확인
- 두 행렬의 크기가 같은지 확인
- 행렬 안에 숫자만 들어 있는지 확인
- 실제 MAC 연산 실행
- 함수 호출과 결과 반환

  ⇒ 측정값은 컴퓨터의 실행 환경과 측정 오차에도 영향을 받음.

### 5.5 추가 실험: CPU에서 2D/1D MAC 비교 (`cpu_test.py`)

**실험 목적:** 실제 NPU를 사용하지 않고, 동일한 MAC 연산을 Python의 2차원 리스트(`matrix[i][j]`)와 평탄화된 1차원 리스트(`matrix[k]`)로 구현했을 때 결과와 CPU 실행 시간이 어떻게 달라지는지 확인했습니다. 이는 **CPU에서 실행한 Python 자료구조 비교**이지 CPU와 NPU의 직접 성능 비교가 아닙니다.

**실험 조건:** 외부 연산 라이브러리 없음, 두 함수 모두 입력 검증 생략, 값이 1인 동일한 N²개 데이터, 실행 전 5회 예열, 각 함수 **30회** 측정 후 평균(ms) 사용. 행렬 생성·평탄화·출력 시간은 측정 구간에서 제외했습니다. 실제 Windows 실행 로그에서 가져온 수치입니다.

| 크기 | 2D 평균(ms) | 1D 평균(ms) | 결과 일치 | 더 빠르게 측정된 방식 |
|---|---:|---:|:---:|---|
| 3×3 | 0.003063 | 0.000510 | True | 1D |
| 5×5 | 0.003827 | 0.002017 | True | 1D |
| 13×13 | 0.009040 | 0.005683 | True | 1D |
| 25×25 | 0.028153 | 0.019690 | True | 1D |
| 100×100 | 0.693723 | 0.446400 | True | 1D |
| 300×300 | 7.240030 | 9.876593 | True | **2D** |

**해석:**

1. 모든 크기에서 `True`가 출력되어 두 방식의 **MAC 계산 결과가 같음**을 확인했습니다. 따라서 데이터 구조를 바꿔도 이 실험의 수학적 결과는 유지되었습니다.
2. 25×25에서는 1D가 2D보다 약 **1.43배 빠르게**, 100×100에서는 약 **1.55배 빠르게** 측정되었습니다(2D 시간 ÷ 1D 시간).
3. 반면 300×300에서는 **2D가 약 1.36배 빠르게** 측정되었습니다(1D 시간 ÷ 2D 시간). 즉, **1차원 접근이 항상 빠르다는 결론은 성립하지 않습니다.**
4. 이런 차이에는 Python 반복문, 인덱싱과 객체 참조, 메모리 할당·캐시, OS 스케줄링 등 여러 요소가 영향을 줄 수 있습니다. 단일 평균 기록만으로 300×300 역전의 원인을 특정할 수 없습니다.
5. 2D와 1D 방식 모두 N²개의 원소에 대해 MAC를 수행하므로 시간 복잡도는 **O(N²)**입니다. 자료구조 변경은 주로 구현·접근 방식과 실제 상수 비용에 영향을 줍니다.
6. `main.py`의 §5.3 측정값과 수치가 다른 이유는 **실험 함수와 측정 조건이 다르기 때문**입니다. `main.py`의 `mac()`은 검증 포함·10회 평균이고, `cpu_test.py`는 검증 제외·30회 평균입니다. 서로 같은 조건의 성능 비교로 해석하면 안 됩니다.
7. 정밀하게 비교하려면 각 조건을 여러 세트 반복하고 평균뿐 아니라 표준편차·중앙값을 확인하며, 전처리(평탄화) 비용을 포함한 전체 처리 시간도 별도 측정할 필요가 있습니다.
8. 이 결과만으로 NPU의 연산 병렬화 효과, 메모리 대역폭 또는 전송 병목을 **실측으로 입증한 것은 아닙니다.** NPU에 대한 설명은 §4.8의 이론적 분석을 참고해야 합니다.

### 5.6 최신 실행 로그 및 재현 방법

2026-11-18의 신규 라벨 단위 테스트에서는 `plus`, `십자가`, 기존 `+`·`cross`·`x`·`X`, 공백·대소문자, 잘못된 값과 자료형 검사 모두 `assert`를 통과해 `라벨 정규화 테스트 전체 PASS`가 출력되었습니다(§4.4 C).

같은 날 이어 실행한 `python main.py`의 JSON 모드에서 `size_5_1`, `size_13_2`, `size_25_1`은 `UNDECIDED`로 FAIL, 나머지 3건은 PASS였습니다. **총 6 / PASS 3 / FAIL 3**으로 기존 판정 결과가 유지되었습니다. 가장 최근 성능 측정 수치는 §5.3에 기재했습니다.

별도 `python cpu_test.py`의 2D/1D 비교 측정 결과는 §5.5에 실었습니다. 재실행 시 운영체제 상태와 Python 실행 환경에 따라 절대 시간은 달라질 수 있습니다. 신규 별칭의 JSON 통합 적용 증빙을 강화하려면 `data.json`의 변경 전후 `expected` 원본 값을 함께 기록해야 합니다.

## 6. 테스트 및 재현성

| 테스트 | 확인 결과 |
|---|---|
| 모드 1: 3×3 십자가 필터·X 필터와 십자가 패턴 입력 | A 5.0 / B 1.0 / A 판정 |
| 입력값 개수가 3개가 아닌 경우 | 오류 안내 후 해당 행 재입력 |
| `a` 등 숫자가 아닌 문자 입력 | 오류 안내 후 해당 행 재입력 |
| 모드 2: 원본 JSON 데이터 분석 | 총 6 / PASS 3 / FAIL 3 |
| 알 수 없는 expected 라벨 | 케이스별 FAIL, 다음 케이스 계속 분석 |
| 패턴 행의 원소 수 불일치 | 케이스별 FAIL, 다음 케이스 계속 분석 |
| `size_5` 필터 누락 | 관련 케이스 2개 FAIL, 다른 크기 계속 분석 |
| 3×3, 5×5, 13×13, 25×25 성능 측정 | 10회 평균(ms) 및 N² 출력 |
| 2D/1D MAC 비교 (`cpu_test.py`) | 6개 크기 모두 계산 결과 `True`, 30회 평균 시간 기록 |
| 신규 라벨 `plus`·`십자가` 단위 테스트 | `assert` 통과, 오류 없이 실행 |
| 기존 라벨·공백·대소문자·잘못된 자료형 회귀 테스트 | `라벨 정규화 테스트 전체 PASS` 출력 |

의도적 오류를 넣는 테스트는 **백업본을 만든 뒤 임시로만** 수행하고, 최종 실행과 제출 전에는 원본 `data.json`을 복원합니다. 측정 시간은 CPU 상태 및 실행 환경에 따라 달라질 수 있습니다.


## 7. 구현상 한계 및 개선 방향

- 현재 콘솔 입력에서는 입력 숫자의 개수와 숫자 변환 여부를 검증하지만, 입력 중 강제 종료나 EOF 같은 상황은 별도로 처리하지 않았습니다.
- 현재 코드에서 `data.json` 파일 자체가 없거나 JSON 문법이 잘못된 경우를 위한 파일 읽기 예외 처리는 별도로 보완할 수 있습니다.
- 현재 `extract_size_from_key()`는 크기 숫자를 추출하지만 `size_N_idx` 전체 문자열의 엄격한 규칙까지 검증하지는 않습니다.
- 현재 `is_number()`는 Python 특성상 불리언(`True`, `False`)도 숫자로 취급하므로, 필요 시 엄격한 검증으로 개선할 수 있습니다.
- 추후 MAC 연산에서 데이터 검증 부분과 실제 곱셈·누적 부분을 분리하면 더 순수한 계산 성능을 측정할 수 있습니다.
- 선택 보너스 중 **2D/1D 접근 비교 실험은 `cpu_test.py`로 수행**했지만, 최종 프로그램 `main.py`에 이 비교 메뉴를 통합하지는 않았습니다. Cross/X 자동 패턴 생성기는 아직 구현하지 않았습니다.

## 8. 학습 소감

이번 미션을 통해 Python의 함수, 리스트, 이중 반복문, 조건문, 예외 처리, JSON 파일 로드, 라벨 정규화와 시간 측정을 함께 연습했습니다. 특히 예상과 다른 결과가 나왔을 때 프로그램 오류인지, 입력 데이터 문제인지, epsilon 비교 정책에 따른 결과인지를 구분하여 확인하는 과정이 중요하다는 점을 이해했습니다. 추가 실험에서는 1D가 대부분의 크기에서 빨랐으나 300×300에서는 반대 결과가 나와, **단 한 번의 성능 측정만으로 일반화하지 않는 태도**가 필요함을 배웠습니다.
